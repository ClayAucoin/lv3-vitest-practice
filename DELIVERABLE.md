I learned from working on the greeting and utility functions that testing is less about “proving my code works” and more about clearly describing how it should behave. Writing tests for `makeGreeting`, `addSignature`, and `toProperCase` made me think about details like capitalization, punctuation, and how to handle long, weird names instead of just the simple "Hello World" message. The `add` and `toSnakeCase` tests did the same thing for numbers and string formatting. I also saw how tests can catch subtle problems that I wouldn't normally think about, like floating point math issues or unexpected characters, before those bugs ever show up in a real app.

Using a red-green-refactor style changed the way I wrote code some of my code. Instead of jumping straight into it and hoping it worked, I wrote a test that failed first that described the next small behavior I wanted, watched it fail (red), and then added just enough code to make it pass (green). I refactored my code after the tests were green knowing I would be warned if I broke something. That kept me focused on small steps. First handle simple names, now mixed case, now long strings, now punctuation in `toSnakeCase`,” and so on. It worked better than the guess-and-check experiment.

I definitely ran into some challenges. Some of them were basic things like typos, parentheses in the wrong place, or tests not matching what the function really does. Others were about edge cases and things like how many underscores I actually wanted from multiple spaces or punctuation, and how to handle capitalization in long names. I overcame those by reading the Vitest error messages carefully, running tests often, and adjusting either the code or the tests once I realized my assumptions were off. In the end, the failures were helpful, each red test forced me to clarify my logic and made me feel more confident that the final functions were correct, not just lucky.
